# exvia 概要设计说明书

需求说明见[需求说明书](requirements.md)。

## 设计原则

整个设计围绕四条原则展开。

第一，中继按不可信组件对待。会话内容在被控端与 CLI 之间加密，中继只做三件事——登记在线机器、撮合会话、搬运密文。它不理解也读不到会话内容，业务逻辑全部在两端。这个定位决定了中继可以被放在任何不被完全信任的机器上而不扩大攻击面。

第二，网络兼容性优先。当前唯一必选的承载方式是标准的 WebSocket over TLS——这是最不容易被出站审查设备区别对待的形态。不依赖 UDP，不引入自定义传输协议。

第三，独立服务模式部署。中继自带 TLS、独占一个可配置的端口，不与机器上已有的 HTTPS 服务复用端口，不依赖前置反代。被控端同样以系统服务方式常驻。部署 exvia 不需要动任何现有服务。

第四，一个仓库产出三个二进制，共享一个协议库，避免两端协议实现对不上。

## 总体架构

```
  操作者本机                                    公网 VPS                          被管机（受限网络）
┌─────────────┐    WSS（出站）          ┌─────────────────────┐    WSS（出站）      ┌──────────────┐
│  exvia CLI  ├───────────────────────►│     exvia-relay      │◄───────────────────┤  exvia-agent  │
│ （仅出站）  │◄───────────────────────┤  自带 TLS，独占端口  ├───────────────────►│  （仅出站）  │
└─────────────┘                        │  系统服务方式运行    │                    └──────┬───────┘
                                       └─────────────────────┘   复用连接上的多条会话流  │
                                                                  每条流 = 一个会话      │
                                                              终端 / 文件 / 端口转发 ────┘
                                   会话内容端到端加密（Noise），中继只见密文
```

几个关键点：

- 全系统只有出站连接。被控端和 CLI 都主动连向中继，被管机和操作者本机都不需要开放任何入站端口。这是能在受限网络里工作的前提。
- 每端一条长连接承载所有会话。连接建立后用 yamux 在其上开多条复用流，一条流对应一个会话（一次终端、一次文件传输、一条转发的 TCP 连接各占一条）。
- 中继撮合之后进入纯搬运模式。会话建立时中继负责把两端的复用流对接起来，之后只做密文转发，不解析内容——事实上它也无法解析。
- 双层加密。外层 TLS 1.3 保护连接元数据与中继通信，内层 Noise 保护会话内容。中继拿不到内层密钥。

三个组件的职责边界：

| 组件 | 职责 | 不做什么 |
|---|---|---|
| exvia-relay | TLS 服务、机器登记、心跳维护、会话撮合与密文搬运 | 不理解、不可读会话内容，不做业务逻辑 |
| exvia-agent | 出站连接维持、端到端加密会话、终端/文件/转发执行、本地密钥保管 | 不监听入站端口，不落地会话内容 |
| exvia CLI | 用户交互、控制面请求、端到端加密会话、本地终端桥接、端口监听 | 不直接连被管机 |

## 部署与运行形态

中继以独立系统服务运行，直接监听一个配置指定的端口（默认 8443，部署时按目标网络的放行策略调整），TLS 由中继内置的 rustls 终止，不需要 nginx/Caddy 等前置反代。

部署在哪里。选址只有一条硬性要求：同时被两类发起方出站可达——受限网络内的被控端、操作者本机。通常就是一台有公网 IP 的 VPS 或云主机，也可以是任何满足可达性的自有设备。它不在任何被管机的内网里，就是两端共同的连接汇聚点。资源要求很低：中继只做 TLS 终止、字节搬运和一个 sqlite 文件，百台规模下 1 核 1GB 内存、几 GB 磁盘足够；真正需要规划的资源是带宽——星型拓扑下所有会话流量（包括文件传输）都从它上面过，中继带宽就是全系统的吞吐上限。

一台中继带多台被管机是默认形态。节点靠登记扩张：每台机器各自走一次 enroll（各用一枚一次性令牌），注册后在中继的机器表里各占一行，`exvia ls` 列出全部在线机器，`exvia shell <机器标识>` 指定操作对象。设计规模为单中继 100 台在线、每台 8 个并发会话。需要管理多组机器时（出口策略不同、或管理面要求隔离），部署多台中继实例即可——被控端注册到哪台就归属哪台，CLI login 到哪台就看到哪台的机器，实例之间互不感知。这是多实例并列，不是集群；集群化与高可用是明确不做的事。

证书与指纹。中继首次启动时自动生成自签证书（有效期足够长），把证书的 SHA-256 指纹打印出来并保存。管理员把这个指纹随注册命令交给被控端和 CLI，双方记录后固定——之后凡是证书指纹对不上的连接一律拒绝。没有正规域名和证书签发流程的依赖，同时获得比"信任公共 CA"更强的中间人防护。改用正规证书（ACME）不改变指纹机制。

伪装页面。中继对普通的 HTTP 请求（浏览器访问、端口扫描）返回一个可自定义的普通静态页面，只有携带正确路径的 WebSocket 升级请求才进入协议流程。对中继端口做人工访问或扫描，看到的是一个普通网站。

服务化。中继与被控端都提供 systemd unit：安装即注册开机自启，进程退出自动拉起，日志进 journald。CLI 是常规命令行程序，不需要服务化。

数据存储。中继持久化用一个 sqlite 单文件（机器表、令牌表、用户表、审计表）。存储内容只有元数据，见后文威胁模型。

## 协议设计

### 分层结构

| 层 | 内容 | 实现方式 |
|---|---|---|
| 传输 | TLS 1.3（自签证书 + 指纹固定） | 中继内置 rustls 直接终止 |
| 连接 | WebSocket 长连接 | 中继用 axum 的 WS 支持；被控端和 CLI 用 tokio-tungstenite |
| 控制面 | 注册、心跳、会话管理等 JSON 消息 | 直接走 WebSocket 文本帧，不进复用层 |
| 复用 | 一条连接上的多条会话流 | yamux |
| 会话 | 端到端加密 + 各类会话的内部协议 | 每条会话流先跑 Noise 握手，再走统一帧格式 |

控制面消息和会话流是分开的：控制消息（注册、心跳、会话请求）是低频的结构化消息，直接用 WebSocket 文本帧传 JSON；会话流是高频字节流，走 yamux 复用，内容端到端加密。两者混在一起会让中继的解析逻辑变复杂，也没有必要。

传输选型与 UDP/QUIC 的定位。出站管控的主战场在 TCP：白名单几乎都是 TCP 中心化的（80/443，偶尔加代理端口）；UDP 的默认姿态是收紧——典型策略为"默认拒绝 + 例外放行"（DNS 常常只许指向内部解析器、NTP 视情况），因为 UDP 无状态、难以有意义地过滤，又是 DNS 隧道、放大攻击和 P2P 的主要载体；不少环境还专门封掉 QUIC（UDP 443）以强制流量走可审计的 TLS 代理，"443 的 UDP"反而是被点名照顾的对象。扫描的重心同样在 TCP：TCP 扫描有握手、快且判定明确，UDP 扫描无握手、结果歧义、慢一个数量级，例行扫描只覆盖少数著名端口。因此 WSS 是当前唯一必选的承载。

但 UDP 不是被放弃，而是按实测结果决定：传输层的可插拔是设计预留（会话协议层对承载类型无感知），当前仅实现 WSS 承载；受限网络到中继的 UDP 443 实测可达且稳定时，QUIC 作为首选传输（与浏览器 QUIC 流量同形，0-RTT 重连、连接迁移，并消除多会话复用在 TCP 上的队头阻塞）；不可达或不稳定时继续用 WSS，QUIC 不启用。届时两种传输共用同一套会话协议，切换是部署参数而非架构变更。

无论哪种，自定义 UDP 协议与 FakeTCP 类伪装都不采用：前者在出站策略里是必拦特征，后者在深度 DPI 下比标准 TLS 更易识别（合成 TCP 流无拥塞行为、协议栈指纹可辨），且属于主动对抗姿态，与"看起来就是普通流量"的目标相悖。

L3 组网（WireGuard 数据面 + eBPF/FakeTCP 隧道）也不并入传输层：它要求被管机 root、可加载 eBPF、可改网卡 offload，合成 TCP 流同样在深度 DPI 下比标准 TLS 更易识别；需要时只做进程隔离的外部集成（GPL 隔离），端口转发已覆盖点到点访问。

### 连接方向与相互发现

谁监听、谁发起。全系统只有一个监听者——中继，它以 TLS 服务端的身份被动接受连接，除此之外任何组件不监听任何端口。被控端和 CLI 都是主动发起方：被控端启动后向中继发起一条出站 WSS 长连接并终身维持；CLI 在每次执行操作时按需发起出站 WSS 连接，用完即断（`exvia forward` 期间维持）。被控端与 CLI 之间不直接建立网络连接，即使正在开会话也没有——会话内容复用两端各自到中继的那条出站长连接，由中继在中间对接。CLI 唯一的本地监听发生在 `-L` 端口转发时，在自己机器的 127.0.0.1 上开一个端口，与受限网络无关。

互相发现靠配置与登记，不靠扫描和广播。

- 被控端找到中继：注册时管理员把中继地址（含端口）和证书指纹写进 enroll 命令，验证通过后保存在本地身份文件，之后每次启动直接连；
- CLI 找到中继：`login` 时同样写入本地配置；
- 中继找到被控端：被控端注册后，中继的机器表里就有"机器标识 ↔ 当前连接"的对应关系，心跳维持在线状态；
- CLI 找到被控端：`exvia ls` 查询的就是中继的登记表；`exvia shell web-01` 时 CLI 把机器标识发给中继，中继在对应被控端的长连接上开一条复用流、递送会话邀请——全程没有任何寻址、广播或探测行为。

这个连接模型的直接好处：被管机在 NAT 后面、在多层防火墙后面都无所谓，只要它出站能到达中继，系统就成立；被管机上不存在任何可被扫描发现的监听端口；会话的建立不产生任何新的网络连接，流量特征就是两条已经存在的长连接。

### 注册与身份认证

被控端的信任链分两步，注册只发生一次：

首次注册。管理员签发一次性令牌，被控端携带令牌、自己的 ed25519 公钥和主机信息（主机名、系统、架构、版本）发起注册。注册命令同时校验中继证书指纹（与管理员提供的比对），通过后才继续。中继校验令牌有效后立即作废它，把公钥和机器信息入库，返回机器标识。令牌泄露的影响面被限制在"一次性、可用后作废"。

日常认证。之后的每次连接分两段验证：先是 TLS 层的证书指纹校验（本地固定值比对，不需要任何第三方 CA），然后中继下发 16 字节随机挑战数，被控端用本地私钥签名应答，中继用库里的公钥验签。没有私钥的冒名者过不了这一步。本地密钥文件权限 0600。

CLI 这边：`exvia login` 用管理员凭证换一个会话令牌存在本地，登录时同样固定中继证书指纹；用户体系提供完整的用户认证和机器授权检查。

认证窗口。中继对"连上了却不完成认证"的连接不给无限耐心：注册、登录、上线握手各有 15 秒的绝对期限（按接通时刻计时，不是空闲计时），超时即断开。这是针对慢速连接悬挂占资源的低配版 DoS 防线；被拒的登录立即返回原因帧，客户端能马上看到错误并退避重试，而不是干等自己的读超时。

### 会话建立流程

以开终端为例：

```
CLI                            中继                             被控端
  │  CreateSession{机器, 终端}    │                                  │
  ├─────────────────────────────►│ 生成会话 ID                       │
  │                              │ 在被控端连接上开一条复用流        │
  │                              │ 发送会话邀请（含 CLI 公钥）──────►│
  │                              │◄──────────── 接受会话             │
  │◄─ 会话就绪 ──────────────────┤ 在 CLI 连接上开对应复用流         │
  │                              │                                   │
  │◄═════ Noise 握手（两端直连，中继只搬字节）══════════════════════►│
  │                              │                                   │
  │ ═══════════ 中继纯密文搬运，两侧复用流对接 ═════════════════════ │
```

会话粒度定得很细：一次 shell 是一个会话，一次文件传输是一个会话，端口转发的每一条 TCP 连接各是一个会话。粒度细的好处是中继的撮合逻辑简单（一对一对接两条流）、Noise 按会话独立握手（互不牵连）、单个会话出问题不影响别的，审计记录也天然按会话拆开。

会话结束时任意一侧发关闭帧，中继拆除对接。

### 各类会话的内部协议

所有会话共用一个帧格式：1 字节类型（数据 / 控制 / 关闭 / 半关闭）+ 2 字节大端长度 + 载荷。整个帧在 Noise 加密之内。半关闭（Shutdown）帧表示发送方在本流上不再发数据，接收方向下游传播写侧关闭（TCP shutdown write）、读侧继续排空并仍可回发数据——转发会话用它把对端的 FIN 传播进隧道对侧。会话共七类（Echo / Pty / Exec / File / Tcpfwd / TcpfwdReverse / Trust），各自有一小段开场约定：

终端会话。开场协商终端类型和初始窗口大小，之后双向透传字节。窗口大小变化（用户拉伸了终端窗口）用控制帧通知对端。远端进程退出时以关闭帧带回退出码。

命令执行会话。开场带上命令和超时，标准输出和标准错误分开标记（载荷首字节区分），结束时带回退出码。

文件传输会话。开场声明方向、路径、文件大小和 SHA-256，之后按 60000 字节分块发数据，每 16 块确认一次进度。接收端全程计算哈希，一致才把临时文件改名落盘。目录树传输复用同一个会话：按条目元数据（相对路径、类型、权限位、mtime）+ 数据块 + 结束标记组织，整棵树只握手一次。单文件还支持断点续传：分片（`<目标名>.exvia-part[-<内容哈希前缀>]`）留在目标同目录，续传时发送端先用控制帧告知实际起点和该前缀的 SHA-256，接收端拿自己的前缀比对——对不上就丢掉最后一个分块再谈，仍对不上则从头传；双方各自重读已收到的前缀以续算整文件哈希，收尾仍以 SHA-256 为准，不一致就丢弃分片而不是落盘。

端口转发会话。开场带上目标地址和端口，被控端去连目标；连不上立刻用关闭帧告知原因，连上之后双向透传，任何一侧关闭即结束会话。

反向转发会话（`forward -R`，ssh -R 语义：被管机侧监听，流量经隧道回到操作者侧）。开场是 CLI 发控制帧带上被管机侧的监听地址与端口，agent 在被管机上绑定监听——成功回一条 Ack 控制帧，失败以关闭帧带回原因。监听期间被管机侧每来一个新接入，agent 经控制面请中继开一对回程复用流（两侧各写 8 字节 sid 前导精确配对）；回程流上 agent 以响应方身份独立完成 Noise 握手，对端公钥与会话邀请不一致（疑似中间人）即丢弃，配对完成后接入的 TCP 连接与 CLI 本机拨号的目标双向透传。CLI 控制流关闭或半关闭即解绑监听，未配对的接入超时自动关闭。

白名单维护会话（Trust）。发起条件本身就是授权——只有签名能通过既有白名单验签的 CLI 发得起这个会话，受信方借此给其他操作者登记钥匙。开场参数带动作（list / add / rm）与目标公钥，agent 在本地改白名单文件；成功后以控制帧回传当前全量公钥列表、随即以关闭帧收尾，动作被拒（例如撤销最后一把钥匙）以关闭帧带回原因。全程不重启 agent，中继无参与权。

回环测试会话（Echo）。无开场约定、参数为空：CLI 发送数据帧，agent 逐帧原样回写，CLI 比对返回载荷一致即记一次往返时延——这是 `exvia ping` 的测量通道；控制帧与半关闭帧忽略，收到关闭帧或流结束即退出。

### 端到端加密

用 `snow` 实现 Noise 协议，选 XX 握手模式配 X25519 + ChaCha20-Poly1305，每条会话流独立握手。握手完成后整条会话流（包括帧头）都是密文，中继不可读。

被控端本地保存两把密钥：ed25519 用于向中继做身份签名认证，X25519 用于 Noise 密钥交换。两把都是注册时一次生成，没有导出和同步逻辑，丢了就重新注册一台"新机器"。

公钥可信性不依赖中继：CLI 第一次与某台机器会话时显示对方公钥指纹并记录，之后指纹变化立即告警拒绝——和 ssh 的 known_hosts 一个思路。中继在会话邀请里互相传递两端公钥只是"介绍人"角色，介绍人可以被绕过校验环节识破。首连的信任窗口可以带外关闭：agent enroll 成功后输出本机 machine_id 与 Noise 静态公钥，并给出一条可直接复制的预置命令（`exvia known add <machine_id> <x25519_pub>`）；操作者在首连前的 CLI 上执行它即完成预置锚定，之后首连从"记录并信任中继介绍"变为"核对预置值"，不符即拒。这是全项目最后一个无带外锚路径的收口——反向（agent 信任 CLI）的锚一直在 enroll 时由 `--trusted-cli-key` 带外固化。

### 断线与重连

被控端断线后按指数退避重连：1 秒起步，每次翻倍，60 秒封顶，附加 ±20% 的随机抖动避免集体同时重连。注册状态持久化在本地，重连走签名挑战，不需要重新注册。

连接断开时其上的所有会话随之终止，CLI 明确报错。不做会话迁移和恢复，ssh 断线也是重连重开。

心跳周期 30 秒，中继 90 秒没收到心跳标记离线。

## 代码结构与技术选型

一个 cargo workspace，四个 crate：

```
exvia/
├── crates/
│   ├── exvia-proto/   # 协议核心：消息定义、帧编解码、复用封装、Noise 封装、密钥管理
│   ├── exvia-relay/   # 中继：TLS 服务、WS 路由、控制面状态机、密文搬运、sqlite 存取
│   ├── exvia-agent/   # 被控端：连接维持、端到端加密会话、终端/文件/转发执行器
│   └── exvia-cli/     # CLI：命令解析、控制面请求、本地终端桥接、端口监听
```

协议库不碰 IO 细节，只做编解码和状态机，三个二进制共用，可以独立做单元测试——协议是最容易出错的部分，单独隔离便于测试。

技术选型（当前 crates.io 稳定版）：

| 用途 | 选型 | 说明 |
|---|---|---|
| 异步运行时 | tokio | 事实标准 |
| 中继 TLS + HTTP/WS | rustls + axum + ws | rustls 直接做 TLS 服务端，自签证书由 rcgen 生成 |
| 出站 WS | tokio-tungstenite | 配 rustls connector，证书指纹校验用自定义 verifier |
| 流复用 | yamux | libp2p 出品，久经验证，自带背压 |
| 端到端加密 | snow | Noise 协议框架，只用标准握手模式 |
| PTY | portable-pty | wezterm 维护的跨平台 PTY |
| 存储 | rusqlite | 单文件数据库 |
| CLI / 序列化 / 日志 | clap / serde / tracing | 常规组合 |

关于 SSH 的取舍：不重新实现 SSH 协议。终端和文件用内置实现（PTY + 自定义分块协议），对接被管机上既有服务（真实 sshd、sftp、数据库）统一走端口转发。这样避开 russh 这个 API 每个版本都在破坏性变动的依赖，功能上也没有损失——需要标准 ssh 工具链的地方，转发一条隧道过去就是了。

## 安全与不可探测性

本章说明系统防的是什么、怎么防，以及能力的边界。

### 威胁模型

系统里有五类位置，分别说明它们能看到什么：

| 位置 | 能看到 | 看不到 |
|---|---|---|
| 通信路径上的网络设备（防火墙、审查网关、旁路抓包） | 存在一条到中继 IP:端口的 TLS 长连接、流量大小与时序 | 任何内容——TLS 之内还有一层 Noise |
| 中继机器（含被攻陷情形） | 哪些机器在线、会话的起止时间、类型、字节数、两端地址 | 任何会话明文——没有内层密钥；也不能主动新建会话——没有可信 CLI 的签名私钥 |
| 被管机 | 一切（它本来就是被控端所在） | — |
| 操作者本机 | 一切（它本来就是 CLI 所在） | — |
| 冒充者 | 无法上线：过不了 TLS 指纹和签名挑战；无法中间人：指纹固定会立刻暴露 | — |

残余暴露：中继掌握元数据（谁在线、何时开了什么会话、传了多少字节）。元数据不加密也不该加密——中继要靠它完成撮合和审计。攻击者拿下中继得到的是"通信关系图谱"，不是通信内容；但它可以拒绝服务（不撮合、乱改路由、踢连接），这一点在协议层无法消除，只能靠部署侧监控。

中继不能自己开会话。agent 判定 CLI 身份不依赖中继在 `SessionInvite` 里"介绍"的 `peer_pub`——那个值由中继提供，TOFU 校验它等于把授权交给中继，拿下中继的攻击者可以自造 x25519 密钥、冒充 CLI 发起会话并拿到全部明文。会话授权用的是不可伪造的会话票据：CLI 用长期 ed25519 身份对 `(machine_id, sid, x25519_pub, user, expires_at, nonce)` 的规范化字节串签名，随 `CreateSession` 交中继原样透传；agent 在 enroll 时把可信 CLI 公钥白名单固化到本机身份文件（中继碰不到），收到邀请后独立验签，并把票据里的 `x25519_pub` 与 Noise `remote_static` 绑定。票据有 60 秒有效期与一次性 nonce（agent 侧去重、过期条目自动清扫），白名单为空时 fail-closed 拒绝所有会话。中继被完全攻陷也只损失可用性与元数据，拿不到命令执行能力。

### 安全机制

双层加密。外层 TLS 1.3（自签证书）保护连接本身；内层每条会话流独立 Noise XX 握手（X25519 + ChaCha20-Poly1305），保护会话内容。即使外层被某种方式剥离（比如审查设备终止 TLS），内层依然是密文。中继没有任何内层密钥。

三处指纹固定。一是被控端和 CLI 固定中继证书指纹（注册/登录时由管理员提供比对值）；二是 CLI 固定每台机器的公钥指纹（首次会话记录，变更即告警）；三是机器标识本身就是公钥指纹，被控端身份与密钥绑定。三处共同封死中间人路径，且都不依赖第三方 CA。

身份认证。被控端一次性令牌注册 + 每次连接的随机挑战签名（见"注册与身份认证"）。令牌可撤销、一次性，泄露影响面最小。

会话授权。中继侧的用户/机器授权表只做"撮合前的粗粒度过滤"，不是最终授权；最终授权是 agent 用部署期白名单对 CLI 票据的验签。CLI 的长期身份落在 `cli-identity.json`（0600），新增操作者或重装 CLI 后把新公钥补进 agent 白名单：优先用白名单内既有 CLI 执行 `trust add` 在线扩容，钥匙全丢等其余情况才重新 enroll，这是把信任锚放在被管机本地的运维成本。白名单用 `trust list/add/rm` 管理；日志里的用户名以 `claimed_user=` 标注——该字段在票据签名覆盖范围内（中继改不了），但它是 CLI 自报的：agent 只证明"这把白名单钥匙报了这名"，不证明名字对应哪个人，授权依据始终是签名。

本地安全。密钥文件 0600；被控端不落地会话内容（终端字节直接转发；文件先进同目录临时文件、校验通过后原子改名，不保留第二份副本）；被控端不监听任何入站端口。

服务加固。agent 的 systemd unit 只保留 `NoNewPrivileges=true`（禁提权），刻意不加 `PrivateTmp` / `ProtectHome` / `ProtectSystem`：文件传输要写真实路径（含 `/home` 下的任意目标目录），私有临时目录与只读文件系统视图会让 `put`/`get` 写不进部署约定的目标，全路径运维能力优先于文件系统隔离。

供应链。不引入 GPL/AGPL 代码；RustDesk、frp 等项目只参考协议设计不抄代码。snow 尚未经过正式安全审计，因此只用它的标准握手模式、不自定义密码原语，把信任面限制在协议本身。

### 不可探测性（流量层面）

能保证的，逐条列出：

1. 内容不可读。双层加密之下，任何中间设备读不到会话内容，也无法篡改（Noise 有完整性保护）。
2. 协议外形标准，且指纹可部署配置。握手是标准 TLS 1.3，载荷是标准 WebSocket 帧，没有自定义协议特征可供 DPI 识别。证书 `CN/SAN` 与 WS 路径是可被扫描的协议指纹；固定值（如 `exvia-relay`、`/_exvia/agent|cli`）会直接暴露服务类型，因此 `--cert-name` 与 `--ws-prefix` 由部署期决定，三端必须一致；默认值（`localhost` / `/_exvia`）仅供开发与回归测试，生产不改等于主动暴露服务类型。此外 TLS 库指纹（JA3/JA4 类）仍是无法消除的残余特征（见下表）。
3. 端口独立。中继独占配置端口，不与现有 HTTPS 服务冲突，也避免把运维流量和正常网站流量混在一起互相暴露。
4. 访问表现正常。对中继端口的普通 HTTP 访问返回正常网页，端口扫描看到的是一个普通 TLS 站点。
5. 流量形态平稳。心跳 30 秒一次、每分钟一条连接上的字节数与正常会话规模一致，没有突发性的扫描行为或异常重试风暴。

按扫描与检测手段逐类分析会不会被扫到：

| 检测手段 | 能发现什么 | 发现不了什么 |
|---|---|---|
| 外部端口扫描（nmap、空间测绘类） | 中继端口上有一个 TLS 服务——开放端口本身是可发现的，这一点无法避免 | 这是什么服务：HTTP 探测得到正常网页，TLS 握手得到一张自签证书，WebSocket 升级得到 404 或认证失败；响应不带任何标识性的 Server 头、版本号和错误特征，没有"这是 exvia"的指纹 |
| 对被管机的端口/主机扫描 | 什么都扫不到——被控端不监听任何端口 | — |
| 被管机出站流量监视 | 一条发往中继 IP:端口的出站 TLS 连接，与系统里包管理器、监控 agent 等程序的出站 HTTPS 在形态上无法区分 | 连接里传的是什么 |
| 旁路流量分析（NDR 类） | 长连接的存在、流量大小与时序；进阶手段如 TLS 指纹（JA3/JA4 类）可以聚类出"非浏览器指纹的长连接"这种弱异常——exvia 用 rustls 默认指纹，不做浏览器伪装，作为残余特征记录 | 会话内容；且 TLS 库指纹只能归到"某类程序"，识别不出具体是什么工具 |
| 主机侧安全工具（HIDS/EDR） | 被控端是一个普通进程，进程、二进制、网络行为完全可见——主机层隐藏明确不在目标内（见需求说明书"安全与不可探测性"） | — |

存在藏不住（端口、连接、进程都是可见的）；身份只有在部署期正确配置证书名与 WS 路径之后才藏得住，否则证书 CN 与固定路径会直接暴露服务类型；即便配置正确，TLS 库指纹与长连接时序仍是可聚类的弱特征。部署上要注意两点：三端统一改掉默认证书名与路径前缀，并把中继端口选在目标网络放行策略允许的范围内，让这条长连接在出口策略上是"合法流量"。

可选的中继隐身加固（部署选项，仅中继侧）。中继是自己完全控制的机器，可以在其网卡上挂一个极小的 XDP 程序做入站过滤：只放行 TLS ClientHello 中 SNI 等于配置域名的连接（或要求握手携带约定魔数），其余一律丢弃。效果有二：外部扫描对该端口只能看到"filtered"（与防火墙规则无法区分），服务对探测完全隐身，比伪装页面更进一步；未认证的探测报文不进入用户态，中继的攻击面与 DoS 暴露同步缩小。实现约百行 eBPF（aya 生态有现成参考），作为部署选项提供、默认关闭。此加固只作用于 TCP/TLS 入口；若启用 QUIC 传输，其入口由协议栈自身拒绝非法探测。被管机侧不使用任何 eBPF——用 eBPF 隐藏主机侧的进程与连接属于主机层隐藏，明确不做。

能力边界：出口处可以观察到"有一条加密长连接指向中继 IP:端口"，连接存在性、流量大小和时间规律无法隐藏；exvia 不是匿名工具，不对抗对出口流量做主动关联分析的审查者。主机层面的隐藏（进程、文件、对抗杀软与 EDR）明确不做。需求说明书"安全与不可探测性"里有同样的声明。

### 设计取舍

自签证书 + 指纹固定换来了"不依赖 CA、中间人防护更强"，代价是指纹要随部署分发出，第一次部署多一步手工操作，证书轮换要重新分发指纹。

每会话独立 Noise 握手换来会话间隔离，代价是一次终端打开多几百微秒的握手开销，可忽略。

TOFU（首次信任）的适用范围刻意收窄：中继证书指纹在 enroll/login 时由管理员带外提供比对值，本就不是 TOFU；真正存在首连中间人窗口的只有会话对端公钥，该窗口由 enroll 回显的 `exvia known add` 预置命令可选关闭——预置后首连改为核对预置值，未预置时回落首连记录（TOFU），之后指纹变化立即告警拒绝。

## 可靠性与错误处理

所有网络操作显式设置超时（建连 10 秒，会话内操作按类型分别设定），不用库的默认值。

被控端把会话执行器隔离开：单个会话 panic 或出错只结束那个会话，不影响主连接和其他会话；磁盘写满、权限不足这类错误以关闭帧带回明确原因，不让 CLI 干等到超时。

同一台机器出现新连接时（比如旧连接断而未死），中继顶掉旧连接并记录告警，避免出现"幽灵连接"导致会话投递错乱。

字节搬运的背压：中继桥接两条复用流是双向逐帧对拷（`tokio::select!` 泵，中间不经过通道），任一方向写慢了，写入端自然阻塞、读臂随之停摆，读写速度差由 yamux 的流控窗口自然反压回去；固定大小的拷贝缓冲之外不做无界缓冲——否则一台慢机器能拖垮整个中继的内存。

版本协商：注册时带上被控端版本，中继发现协议不兼容时明确拒绝并提示升级，而不是静默解析出错。

## 运维可观测性

指标端点。中继可选开启 `--metrics-listen <地址>`，输出运行指标：在线机器数、活跃会话数、累计会话与传输字节计数、事件计数等。默认关闭；开启时只允许绑定回环地址，绑定非回环地址直接启动失败（fail-closed），远程查看走 ssh 隧道——不为可观测性给公网多开一个面。

生命周期提醒。证书与令牌这类"到期才爆"的东西在启动时就检查：中继证书的有效期记录在旁挂元数据（`relay-cert.json`，生成证书时写入），剩余不足 30 天或已过期，每次启动打印提醒与轮换步骤。TLS 层刻意不做硬过期校验——身份由指纹固定保证，证书过期不该让全系统瞬间下线。管理员令牌超一年未轮换同样提示，轮换后旧令牌立即作废。

审计导出。`export` 子命令把审计数据导出为便于归档的格式，配合"中继只存元数据"的边界，导出物也不含任何会话内容。

故障排查以日志为准：分级可配置，上线/离线、会话开闭、认证失败、路径安全拒绝等关键事件都有结构化记录。

## 命令行设计

```
exvia login --server wss://relay.example.com:8443 --fingerprint <中继指纹>   # 登录中继（固定证书指纹）
exvia pubkey                                        # 打印本 CLI 的长期公钥（登记进 agent 白名单用）
exvia logout                                        # 登出：吊销中继侧会话令牌、清空本地凭证（身份密钥保留）
exvia ls                                            # 在线机器列表
exvia ping <机器>                                   # Echo 通道连通性测试（往返时延）
exvia shell <机器>                                  # 交互终端
exvia exec <机器> -- <命令...>                      # 一次性命令（<机器> 支持逗号分隔多机并发批量执行）
exvia exec -t <机器> -- <命令...>                   # 强制 PTY（ssh -t 语义，单机；退出码与超时语义不变）
exvia put <机器> <本地...> <远端>                   # 上传文件（多源/通配符；目录与多源走树协议）
exvia put <机器1,机器2> <本地...> <远端>            # 多机分发（同一组源并发传到每台；逐机汇总，任一失败整体非零）
exvia get <机器> <远端> <本地>                      # 下载文件（>1MiB 时 stderr 显示进度）
exvia get <机器> '远端/*.log' <本地目录>/           # 远端尾分量通配（agent 匹配后按树协议回传，落本地目录）
exvia forward -L 8222:localhost:22 <机器>           # 正向端口转发（-L/-R 可重复，前台，Ctrl-C 退出）
exvia forward -R 8888:localhost:3000 <机器>         # 反向端口转发（被管机侧监听，CLI 本机拨目标）
exvia alias add <名字> <机器标识>                   # 机器别名（本地配置，离线可用）
exvia sessions                                      # 中继上的活跃会话列表（admin 看全量）
exvia close <sid>                                   # 终止一个活跃会话
exvia trust list/add/rm <机器> ...                  # 管理被管机上的受信 CLI 公钥白名单
exvia known add/list/rm <别名或id> ...              # 本机 TOFU 台账（known_agents.json，纯本地）；add 在首连前预置公钥（命令随 enroll 输出给出）
exvia completion bash|zsh|fish                      # 输出 shell 补全脚本（静态，子命令一级）

exvia-agent enroll --server wss://...:8443 --token <令牌> --fingerprint <中继指纹>
exvia-agent run                                     # 被控端常驻（服务方式）

exvia-relay serve --listen 0.0.0.0:8443             # 启动中继（首次启动打印证书指纹）
exvia-relay token create --label <用途>             # 签发注册令牌
exvia-relay token list / token revoke <编号>        # 管理令牌
```
